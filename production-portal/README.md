# Production Portal - The Mirror CTF

## Overview

The **Production Portal** is a legitimate-looking customer web application that The Mirror actively defends. This creates a realistic active defense scenario with **two paths to victory** in the CTF.

## Two Paths to Victory

### Path 1: White Hat (Legitimate Access) 🎯

1. Discover valid credentials through OSINT/social engineering/hints
2. Login successfully to the customer portal
3. Explore the authenticated dashboard
4. Find the admin configuration page
5. **Win**: Capture the production API key flag

**Flag location**: `/admin/config` endpoint (requires authentication)  
**Flag format**: `flag{production_master_key_<random>}`

### Path 2: Black Hat (Attack & Get Caught) 🪞

1. Scan or attack the production portal (directory brute force, SQLi, etc.)
2. The Mirror AI agent detects reconnaissance patterns
3. Agent executes `redirect-to-honeypot` action via nftables DNAT
4. Attacker is now hitting the honeypot but thinks it's still production
5. Honeypot logs all their actions
6. Agent creates incident in database with their IP
7. Attacker discovers dossier URL (from honeypot hints)
8. **Win**: Find their own incident report with their dossier flag

**Flag location**: Dossier web app at `/dossiers/<incident_id>`  
**Flag format**: `flag{RIPOSTE_COUNTER_RECONNAISSANCE_<incident_id_suffix>}`

## The Redirect Mechanism

### How It Works

```
Internet → Production Portal (port 8000)
              ↓
         Mirror Agent (log watcher)
              ↓
         Detects attack patterns
              ↓
         Executes nftables DNAT:
         ip saddr <attacker> tcp dport 8000 → dnat to honeypot:8080
              ↓
         Attacker sees same URL, hits honeypot backend
              ↓
         Incident created in database
              ↓
         Dossier contains AI-generated narrative
```

### Attack Detection Triggers

The Mirror agent redirects when it detects:
- Scanning tools (Nmap, Nikto, SQLMap user-agents)
- Directory brute forcing (multiple 404s)
- SQL injection attempts
- Abnormal request patterns
- High-frequency requests

### nftables DNAT Rule

When an attack is detected, the agent executes:

```bash
nft add rule ip nat prerouting \
  ip saddr <attacker_ip> tcp dport 8000 \
  dnat to simple-honeypot.cyber-riposte.svc.cluster.local:8080 \
  comment "mirror: redirect to honeypot"
```

**Result**: Same URL (`production-portal-cyber-riposte.apps...`), different backend (honeypot)

## Deployment

### Build the Image

```bash
make build-production-openshift
```

This creates a BuildConfig and ImageStream in the `cyber-riposte` namespace.

### Deploy via Helm

The production portal is included in The Mirror Helm chart:

```bash
helm install the-mirror ./helm/the-mirror \
  -n cyber-riposte \
  --create-namespace \
  --set productionPortal.enabled=true
```

### Enable Traffic Redirection

To enable The Mirror's traffic redirection capability:

```bash
helm install the-mirror ./helm/the-mirror \
  -n cyber-riposte \
  --set productionPortal.enabled=true \
  --set agent.enableRedirect=true
```

**Note**: `enableRedirect=true` grants the agent NET_ADMIN capability to run nftables commands.

### Get the Portal URL

```bash
oc get route production-portal -n cyber-riposte -o jsonpath='{.spec.host}'
```

## Environment Variables

The portal is configured via:

- `PORT` - HTTP port (default: 8000)
- `SECRET_KEY` - Flask session key (auto-generated)
- `MASTER_API_KEY` - The production flag (auto-generated in flag{} format)

Secrets are auto-generated by Helm if not provided.

## Architecture

### Why This Matters

The current CTF setup only has a honeypot - players go straight to fake content. There's no "real" application to protect, so The Mirror's redirect capability isn't demonstrated.

The production portal shows what The Mirror actually **does** - it protects real applications by detecting attacks and redirecting malicious traffic to a honeypot.

### Full Active Defense Stack

For the complete active defense experience:

1. **Production Portal** - Real web app with actual secrets
2. **Mirror Agent** - AI detection engine watching logs
3. **nftables** - Traffic redirection (DNAT)
4. **Honeypot** - Fake environment for attackers
5. **Dossier** - AI-generated incident reports
6. **Database** - Evidence collection and storage

## Security Considerations

### Intentional Vulnerabilities

The portal has **intentional** weaknesses for CTF purposes:

- Credentials in HTML comments
- Weak password reuse
- Hints in robots.txt
- Admin config accessible to all authenticated users

**Do not** deploy this in production!

### NET_ADMIN Capability

When `enableRedirect=true`, the agent pod gets NET_ADMIN capability to run nftables. This is required for traffic redirection but increases the pod's privilege level.

**Use this only in isolated CTF environments, not in production clusters.**

## Troubleshooting

### Portal Not Accessible

```bash
# Check pod status
oc get pods -l app=production-portal -n cyber-riposte

# Check logs
oc logs deployment/production-portal -n cyber-riposte

# Check route
oc get route production-portal -n cyber-riposte
```

### Redirect Not Working

```bash
# Check if redirect is enabled
helm get values the-mirror -n cyber-riposte | grep enableRedirect

# Check agent logs for nftables errors
oc logs deployment/mirror-agent -n cyber-riposte | grep nft

# Check agent has NET_ADMIN
oc get pod -l app=mirror-agent -n cyber-riposte -o yaml | grep -A5 capabilities
```

### Login Not Working

Check the auto-generated secret:

```bash
oc get secret the-mirror-production-secrets -n cyber-riposte -o yaml
```

The default credentials (admin/wealth_of_nations) are hardcoded in the app.
